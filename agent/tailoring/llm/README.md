# llm

Ollama client wrapper — the only place `tailoring/` actually talks to the local model.

`llm_ollama(user_prompt: str, system_prompt: str, model: str = "gemma3", temperature: float = 0.2) -> str` in `client.py` sends one `system` message and one `user` message via a **module-level, reused** `AsyncClient` (not one constructed per call — verified 2026-08-04) with `options={"temperature": temperature}` (kept low by default since these calls need to stay factual, not creative), and returns `response.message.content`. Deliberately generic — it doesn't know or care which of the three calls (resume, cover letter, application/form-fields) it's serving; `prompts/` builds the specific `user_prompt` for each, and the caller invokes this function three times per posting (decided 2026-08-04 — see `../README.md`).

**Failure handling: one `except Exception`, raises `OllamaError` (revised 2026-08-05, replaces the earlier four-case `return None` design).** The four failure modes the earlier version distinguished by separate `except` clauses — `ResponseError` (bad model name, bad request), `ConnectionError` (Ollama catches `httpx.ConnectError` internally and re-raises it as a plain built-in `ConnectionError`), `httpx.TimeoutException` (not wrapped by the library, propagates as-is — the one actually expected to fire in practice, since this project runs CPU-only inference, see `../../CLAUDE.md`'s tech stack section), and a generic catch-all — are now caught by one `except Exception` and re-raised as one `OllamaError`. **The caller must handle this explicitly (decided 2026-08-05):** `llm_ollama` no longer returns `None` on failure — a caller that used to write `if response is None:` now needs `try`/`except OllamaError`, matching how `tailoring/generate.py` already handles `write_resume`/`write_cover_letter`'s own uncaught failure modes (`playwright.async_api.Error`/`pypdf.errors.PyPdfError` → `WriteError.RENDER_FAILURE`) — `OllamaError` maps to the new `WriteError.LLM_FAILURE` (see `../write/README.md`) the same way. **`llm_ollama` itself doesn't log the failure (decided 2026-08-05, avoids double-logging).** `raise OllamaError(str(e)) from e` preserves the original exception as `__cause__`, so whichever `except OllamaError` finally handles it (currently `generate.py`'s `logger.exception(...)`) gets the full chain — original exception type, message, and traceback plus `OllamaError`'s own — in one log call. An earlier version had this function log the failure itself *and* raise; since the exception always ends up caught and logged somewhere, that meant every LLM failure was logged twice for no reason.

**Dependency: `ollama` (added 2026-08-04)** — declared in `../../pyproject.toml`, installed in `../../venv`, frozen in `../../requirements.txt`. Previously imported but not installed or declared anywhere; running any code that imported this module would have failed with `ModuleNotFoundError`.

Named `client.py`, not `ollama.py` — the latter would shadow the `ollama` pip package for any absolute import inside this file (`from ollama import AsyncClient` importing itself instead of the real package).

`OLLAMA_HOST` env var controls the target host, defaulting to `http://localhost:11434` for local dev; set to `http://ollama:11434` (or equivalent) when running under the project's planned k3s/minikube deployment (see the Architecture section of `../../CLAUDE.md`).

Scratch/prototype — role names and the single-string return format may still change as `prompts/` and `write/` firm up. See `../README.md`.

# prompts

Builds the four prompt strings fed into `llm/client.py`'s `llm_ollama` — one shared system prompt, three call-specific user prompts.

**Output format: JSON for all three calls.** Each user prompt instructs the model to return a JSON object of fields, not raw markup or freeform text — `write/` parses that JSON and maps fields into a Jinja2 HTML template (or, for `application.py`, hands the JSON straight to `form_automation/`). Escaping is Jinja2's job at render time, not a manual per-field step or the model's concern.

## Files

- `system_prompt.py` — rules shared identically across all three calls: the honesty constraint (plus naming gaps directly — scoped to form answers, since letters get their gaps from code) (organize/format/select from `source_of_truth` content only, never invent), the prompt-injection framing that labels the posting (`<job_posting>`), form questions (`<questions>`), and posting text quoted elsewhere as untrusted data, and the JSON-output instruction. `_shared.py`'s `format_posting()` sends only the posting's content fields (`posting_content()` — no ids, urls, or `raw`), and escapes `<`/`>` in all of that untrusted text (form field ids included) (`\u003c`/`\u003e` in the posting's JSON, HTML entities elsewhere), so it can't close a tag early and pose as prompt structure.
- `resume.py` — user prompt for the resume call. The resume's `summary` starts from the candidate's own `profile.json` `summary` (passed in directly, in a `<candidate_summary>` block): shortened and tailored, with no added titles, seniority, years or expertise — written from scratch, it opened with the genre's "Experienced backend engineer…". Built from the facts that cleared matching's threshold (`matching_facts` — result dicts; the prompt reads each one's `doc_id` and `content`) plus the one-page and template-structure constraints for `write/templates/resume.html`. `RESUME_SCHEMA`:
  - `summary` — matches `profile.json`'s `summary` string.
  - `skills` — an object keyed by category (not a flat array), matching how each skill fact is actually indexed, so the template's grouped Skills section can be reconstructed from what the model is given.
  - `projects[]` — `name`/`dates`/`tech`/`description`/`bullets`, plus `status` and `repo` (real project facts carry both).
  - `certifications[]` — each cert is its own fact; the resume's Training & Certificates section is LLM-filled from these rather than hardcoded.
  - **Deliberately excluded:** education and professional-experience facts. Both can legitimately surface among a posting's matching facts, but the resume template has no section for them — this candidate's gaps there (GPA, in-progress degree, no professional experience) belong in the cover letter's code-written gaps paragraph when the posting asks about them. `generate()` now removes those facts from the resume's input in code (see `../README.md`); the prompt's instruction not to place them in the resume stays as a backstop.
- `cover_letter.py` — user prompt for the cover letter call. The model writes only a `CoverLetterDraft`: `why` (1–2 sentences continuing a code-written opening sentence), `experience`, and — only when the posting quoted a years requirement — an optional `stack_gap` sentence naming the narrower stack gap, given only the posting's quoted requirement(s) — not the gap's `guidance`, whose example sentence (about TypeScript) could otherwise be copied into a letter for another stack. It never writes the opening sentence, the closing, or the gaps paragraph (code writes those; see `../write/README.md`), and is told not to mention gaps at all. Input: `matching_facts` minus non-fit facts (see `../README.md`). Soft style rules: no generic filler, match the posting's tone where direct, keep it short.
- **Shared honesty rules (system prompt, tightened 2026-09-30 and 2026-10-07 after live runs):** the posting's wording describes the job, never the candidate (the model once called the candidate "frontend" because the posting did); a technology belongs to a project only if that project's own fact names it (the run had Go/Python projects credited with React/Node experience); every hedge a fact carries stays with it ("Kubernetes (experimental)", not "Kubernetes"), and no claim gets stronger than its fact ("extensive", "production", "years of"); named filler phrases banned. The resume and application prompts repeat the attribution rule where it applies.
- `application.py` — user prompt for free-text/behavioral screening-question answers. Deterministic questions (visa, salary, EEO) never reach this — answered directly from `source_of_truth/`. Returns JSON keyed by field id: `{field_id: answer}`; each question may carry an optional `max_length`.

Status: all four written and exercised in live runs against local Ollama (7B, then 14B); wording is still being tightened against what those runs show. See `../README.md`.

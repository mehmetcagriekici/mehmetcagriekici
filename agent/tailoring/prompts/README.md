# prompts

Builds the four prompt strings fed into `llm/client.py`'s `llm_ollama(user_prompt, system_prompt, model, temperature)` — one shared system prompt, three call-specific user prompts (decided 2026-08-04 — see `../README.md`).

**Output format: JSON for all three calls (decided 2026-08-04).** Each user prompt must instruct the model to return a JSON object of fields, not raw markup and not an unstructured text blob — `write/` parses that JSON and maps fields into a Jinja2 HTML template (or, for `application.py`, hands the JSON straight to `form_automation/`). This was chosen over raw-markup output specifically to keep escaping deterministic code's job, not the model's — under the current Jinja2-with-autoescape design (decided 2026-08-05, see `../write/README.md`) that escaping happens automatically at render time, not via a manual per-field step; the concern is the same one LaTeX-escaping used to address (an unescaped model output shouldn't be able to break the render or corrupt the layout), just handled differently now that rendering is Playwright/HTML rather than `pdflatex`.

**Resume schema built from `source_of_truth/profile.json` and `matching/document_builder/document_builder.py`'s actual fact shapes (decided 2026-08-04), not guessed from the template alone.** `RESUME_SCHEMA` in `resume.py`:
- `summary` — matches `profile.json`'s `summary` string.
- `skills` — an object keyed by category (`{"backend": [...], "ai_ml": [...], ...}`), not a flat array — matches how `_skill_documents` actually indexes each skill fact (`{"category": ..., "skill": ...}`), so the Generator can reconstruct the grouping the template's Skills section expects (`\textbf{Category:} skill, skill, ...`) straight from what it's given.
- `projects[]` — `name`/`dates`/`tech`/`description`/`bullets` map onto the `\project{name}{dates}{tech}` macro (arg order corrected 2026-08-04, was previously documented backwards) plus its following description line and bullet list; `status` and `repo` were added after checking `_project_documents` — real project facts carry both (e.g. `"status": "in development"`, `"repo": "https://github.com/..."`), and the template does render them (status inline in the name, repo linked off the last bullet), so the earlier 4-field schema was actually missing data the facts already carry.
- `certifications[]` — new. `_certification_documents` indexes each cert as its own fact, and the resume template's `Training & Certificates` section (previously assumed static, now `write/templates/resume.html` — see `../write/README.md`) renders exactly this shape — so certs are now LLM-filled like every other section, not hardcoded.
- **Deliberately excluded: education and professional-experience facts.** `_education_document` and `_experience_document` index these too, and either can legitimately surface in `hybrid_search`'s top-N for a posting that mentions degree or experience requirements — but the resume template has no section for them, and this candidate's known gaps here (GPA, in-progress degree, no professional experience) are already the cover letter's job via its mandatory `gaps` field (see `cover_letter.py`). `resume.py`'s prompt explicitly tells the model not to place such facts anywhere in the resume output, precisely because they can show up in its input.

- `system_prompt.py` — general rules and safety, shared identically across all three calls: the honesty constraint (organize/format/select from `source_of_truth` content only, never invent a fact — same principle as the root repo's `CLAUDE.md` honesty rules), the prompt-injection framing that wraps raw job-posting text as labeled untrusted data rather than instructions (see the Prompt injection defense section of `../../CLAUDE.md`), and the JSON-output instruction shared by all three calls.
- `resume.py` — user prompt for the resume call. Built from the top-N `(id, content)` Documents `hybrid_search` returns for the posting (see `../README.md`'s Generator input note) plus the one-page and template-structure constraints for `../write/templates/resume.html`. Returns JSON — see the Resume schema note above.
- `cover_letter.py` — user prompt for the cover letter call. Same top-N input, plus the cover letter's hard rules (mandatory gaps paragraph, one page) and soft style rules (3-4 short paragraphs, no generic-enthusiasm filler, match the posting's tone where direct) — see the Cover letter section of `../../CLAUDE.md`. `COVER_LETTER_SCHEMA`: `opening`/`experience`/`gaps` (omitted when no mismatch applies)/`closing`.
- `application.py` — user prompt for free-text/behavioral screening-question answers (e.g. "tell me about a time you solved a bug"). Deterministic screening questions (visa, salary, EEO, etc.) never reach this — they're answered directly from structured `source_of_truth/` fields, no LLM involved. Returns JSON keyed by field id: `{field_id: answer}`; each question may carry an optional `max_length`, rendered inline and backed by one shared instruction to respect any stated limit.

All four are written (decided 2026-08-04, see `system_prompt.py`'s injection-defense and missing-fact rules, and the Resume schema note above) — still scratch/prototype wording, not yet exercised against a real model. See `../README.md`.

# write

Takes each call's JSON output (decided 2026-08-04 — see `prompts/README.md`'s Output format note) and turns it into that call's final artifact.

For the resume and cover letter calls: `write_resume(llm_response, personal, output_path)` and `write_cover_letter(llm_response, personal, company, output_path)` in `write.py` each take the raw JSON **string** straight from `llm/client.py`'s return value — no separate parsing/wiring module, since the only thing between "LLM string" and "validated data" is `json.loads()` + a `pydantic` model, both cheap enough to belong inside `write.py` itself (decided 2026-08-05). Each function `json.loads()`s the string, validates it against a `pydantic` model (`Resume`/`CoverLetter` in `write.py`, mirroring `RESUME_SCHEMA`/`COVER_LETTER_SCHEMA` in `prompts/README.md`'s Resume schema note), fills a Jinja2 HTML/CSS template (`templates/resume.html` / `templates/cover_letter.html`, plus shared `templates/_style.html` / `templates/_macros.html` partials), and renders it to PDF via Playwright print-to-PDF. **Templating mechanism: Jinja2 with autoescape (decided 2026-08-05)** — chosen over manual string building specifically so escaping (`<`, `>`, `&`, quotes — the deterministic-code job LaTeX-escaping used to fill, see `../README.md`, `../../CLAUDE.md`) is handled by the templating engine automatically rather than relying on every interpolated field being escaped by hand; verified against real LLM-shaped input (`<`/`&`-containing strings render as literal text, not markup) — Jinja resolves `foo.bar` via attribute access, so this is unaffected by the switch to `pydantic` model instances below. `personal` is `profile.json`'s `personal` block (name/email/phone/location/github/linkedin, shared header on both documents). The templates' structure carries over from the old LaTeX-era design conceptually, just not its macro syntax: one block per `projects[]` entry (name, dates, tech, description, bullets, with `repo` linked off the last bullet and `status` folded into the name when present); `skills` grouped by category into one line each (`_category_label()` in `write.py` maps known category keys like `ai_ml`/`devops` to `AI/ML`/`DevOps` rather than a naive title-case, since profile.json's actual keys don't title-case cleanly); `certifications[]` filling a Training & Certificates section. The old `resume_template.tex`/`cover_template.tex` LaTeX files are deleted, fully superseded.

**Return type: `WriteResult(path: str | None, error: WriteError | None)` (decided 2026-08-05), not bare `str | None`.** A caller needs to distinguish *why* a call failed, not just that it did: `WriteError.INVALID_JSON`/`VALIDATION_ERROR` mean the LLM response was unusable — there's no real content, so this can't route through the review-email design (`../README.md`, `../../CLAUDE.md`), which shows the full generated package inline and has nothing to show for a broken response. `WriteError.OVERFLOW` means the opposite: real, valid content that's simply too long — the case the review-email design actually exists for. Collapsing all three into one `None` would make that distinction invisible to whatever eventually calls these functions.

**One-page enforcement (decided 2026-08-04): render first, then check the rendered PDF's page count via `pypdf`**, since Playwright's `page.pdf()` doesn't report a page count directly the way `pdflatex` did. Rendering deliberately does **not** clip overflow with CSS — an earlier draft used `overflow: hidden` on the page body to force a single page, but that was rejected: it silently truncates content instead of surfacing the failure, and a resume cut off mid-sentence must never ship unnoticed. Content is left free to flow past one page; a resulting page count other than 1 logs a warning and returns `WriteResult(path=None, error=WriteError.OVERFLOW)`, rather than a hard compile failure the way a broken LaTeX macro would have been. Routing an overflow onward to the user (the email + approve/reject step described in `../README.md`) isn't built yet — that's `review_gate`'s job, not this module's.

For the application call: `parse_application_answers(llm_response)` — the JSON (`{field_id: answer}`) is handed to `form_automation/` directly — no template, no PDF, so no `WriteResult`/no page-count check either. **No pydantic model with named fields (decided 2026-08-05)**, unlike `Resume`/`CoverLetter`: `field_id`s are posting-specific (whatever fields that job's actual application form has), not a fixed schema, so there's nothing to name model fields after. Validated structurally instead, via `pydantic.TypeAdapter(dict[str, str])` against exactly what `prompts/application.py`'s prompt promises ("a JSON object mapping each field_id to its answer as a string") — same `json.loads()`-then-validate two-step and the same `WriteError.INVALID_JSON`/`VALIDATION_ERROR` distinction as the other two calls, returned as `ParseResult(answers: dict[str, str] | None, error: WriteError | None)`. `WriteError.OVERFLOW` doesn't apply here — there's no page to overflow — so this function never produces it. `form_automation/` (not yet built) is the intended consumer of `.answers`; for now this only validates and returns the dict.

Exercised directly (not yet against a real Ollama response). `write_resume`/`write_cover_letter`: valid JSON containing `<`/`&`-bearing strings and real `profile.json` contact data, rendering to one page (`WriteResult(path=..., error=None)`, confirms escaping and rendering); syntactically invalid JSON (`WriteError.INVALID_JSON`); valid JSON missing a required field, e.g. `summary` (`WriteError.VALIDATION_ERROR`); valid JSON with enough content to overflow one page (`WriteError.OVERFLOW`) — each asserted independently, plus a regression check that the shared `WriteError` refactor didn't break either function. `parse_application_answers`: a valid `{field_id: answer}` dict (`ParseResult(answers={...}, error=None)`); invalid JSON syntax (`WriteError.INVALID_JSON`); a non-string answer value and a non-dict payload, both `WriteError.VALIDATION_ERROR`. See `../README.md`.

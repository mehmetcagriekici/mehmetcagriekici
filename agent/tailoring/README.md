# tailoring

Generates a per-job resume variant and cover letter from profile-store facts, plus free-text/behavioral screening-question answers. Reorders/rephrases/emphasizes only — never adds a fact not present in `source_of_truth/`.

**Pipeline role: Application Generator (decided 2026-07-22).** Second stage of `Data -> Hybrid Search -> Application Generator -> Application Controller -> Application API`. Runs **unconditionally** on every posting that clears `matching/`'s single `hybrid_search` step — it has no say in fit, only in generation. Its output goes to `review_gate/` (the Application Controller) for a honesty/relevance check before anything reaches `form_automation/` (the Application API).

**Generator input (decided 2026-08-04, supersedes the id-resolution design in `matching/README.md`'s Types section):** the Generator consumes the top-N `(id, content)` `Document` pairs exactly as `hybrid_search` returns them — no separate resolve-by-id step back to a structured `source_of_truth` record. This holds cleanly because `document_builder` already builds one `Document` per *atomic* fact (`content` is `json.dumps` of that single fact, not a bundle of several), so the flattened form loses no structure worth resolving. N itself isn't a parameter this module owns — it's whatever fact set cleared `matching/`'s threshold for that posting (count varies per posting; see `../matching/README.md`).

**Three separate LLM calls, not one (decided 2026-08-04):** one Ollama call each for the resume, the cover letter, and free-text/screening-question form-field answers (the `application` prompt) — not a single combined call. All three share the same `system` prompt (general rules and safety, including the prompt-injection framing for raw job-posting text — see the Prompt injection defense section of `../CLAUDE.md`) and differ only in the `user`-role content prompt. Deterministic screening questions (visa, salary, EEO, etc.) skip the LLM entirely and are answered directly from structured fields in `source_of_truth/` — only the generative side (resume, cover letter, free-text/behavioral answers) goes through these calls.

**Language: Python** — internal module of the shared Python service (see tech stack in `../README.md`). Local LLM via Ollama, CPU-only, capping realistic model size to roughly 7-8B quantized (current scratch default: `gemma3`, see `llm/README.md`).

Behavioral answers draw on `projects-detail.json` and `general-stories.json` (see `../source_of_truth/README.md`) for real incident-level material rather than extrapolating from feature bullets. For known weak spots in the profile (in-progress degree, no professional experience, GPA, sponsorship need), generation draws on `known-gaps.json` — no special-casing needed, since gap facts are indexed into `source_of_truth` like everything else and naturally surface in `hybrid_search`'s top-N whenever a posting's own language actually touches that gap (e.g. an experience-years requirement pulls in the "no professional experience" fact on its own). No caching for now — every answer regenerates fresh each time.

**Output format: PDF** (decided 2026-07-26), via Playwright print-to-PDF (decided 2026-08-04, replaces an earlier LaTeX/`pdflatex` design — see `../CLAUDE.md`; the root cover-letter workflow is unaffected and stays on LaTeX). The LLM itself returns JSON (decided 2026-08-04 — see `prompts/README.md`'s Output format note, `write/README.md`); `write_resume()`/`write_cover_letter()` (in `write/write.py`) take that JSON **string** directly — `json.loads()` + `pydantic` validation against `RESUME_SCHEMA`/`COVER_LETTER_SCHEMA` live inside `write.py` itself rather than a separate parsing/wiring module (decided 2026-08-05: the string-to-validated-data step is cheap enough that a dedicated module for it would be pure overhead) — then fill a Jinja2 HTML template (decided 2026-08-05, autoescape handles escaping — see `../CLAUDE.md`) and render it. The resume fills a fixed structure (one block per project plus a summary/skills section); the cover letter is genuinely freeform prose within a style shell (header, date, greeting, closing) since it doesn't reduce to a repeatable structural pattern. Built and tested end-to-end against real `profile.json` contact data, including malformed-input cases (bad JSON syntax, valid JSON missing a required field). The application call's `{field_id: answer}` response is handled the same way, minus the rendering: `parse_application_answers()` (also in `write/write.py`) validates it structurally via `pydantic.TypeAdapter(dict[str, str])` — there's no fixed schema to name model fields after, since `field_id`s are posting-specific — and returns `ParseResult(answers, error)`; `WriteError.OVERFLOW` doesn't apply here (no page to overflow). It hands nothing off yet: `form_automation/` (not built) is the intended consumer of `.answers`.

**Orchestration built for all three calls (2026-08-05): `generate.py`'s `generate(facts, job_posting, personal, questions) -> GenerateResult`.** Calls the LLM once per call (no retry, for any `WriteError` — decided ahead of writing this: overflow already had an explicit no-retry rule, and extending it to `INVALID_JSON`/`VALIDATION_ERROR` means `generate()` never needs to branch on *which* error came back, just whether one did; the error-type distinction stays meaningful for whoever consumes the result afterward — `review_gate`, the end-of-run report, see `../CLAUDE.md`'s Review gate section for its "submitted / matched-but-not-submitted / skipped / errors" categories — not for retry control flow), passes each raw response straight to `write_resume()`/`write_cover_letter()`, and aborts the remaining steps as soon as one doesn't produce a result — an LLM failure or a failed render both stop the sequence rather than continuing to (say) generate a cover letter for an application whose resume never rendered. `GenerateResult(resume, cover_letter, application)` distinguishes "never reached" (`None`) from "reached and failed" (a `WriteResult`/`ParseResult` with `.error` set), mirroring `write.py`'s own `WriteResult` design. **`generate()` deliberately has no blanket `except Exception`, and no implicit `if x is None:` checks either (revised 2026-08-05)** — every expected failure is caught explicitly, by its specific type, at the exact call site: `llm_ollama()` (which itself now raises `OllamaError` rather than returning `None`, see `llm/README.md`) is wrapped in `try`/`except OllamaError` → `WriteError.LLM_FAILURE`; each `write_resume()`/`write_cover_letter()` call is wrapped in `try`/`except (playwright.async_api.Error, pypdf.errors.PyPdfError)` → `WriteError.RENDER_FAILURE`, since those are infrastructure failures during rendering itself that `write.py` doesn't catch. Anything else is a genuine bug and is left to propagate as a real exception rather than being silently absorbed into a result that would look identical to a normal graceful failure. **The application call is wired in too (2026-08-05), via a `questions` parameter (decided 2026-08-05: `generate()` doesn't source `questions` itself — that's still `form_automation/`'s job, reading the actual application form, and it still doesn't exist — the caller supplies the list instead, deferring that dependency rather than blocking on it).** Same `try`/`except OllamaError` pattern as the other two calls around the LLM call; `parse_application_answers()` itself is synchronous and has no Playwright/pypdf failure mode to catch, since there's no rendering step for it. **One page is a hard constraint** on every generated document, enforced by rendering first (content left free to flow past one page) then checking the rendered PDF's page count via `pypdf` (decided 2026-08-05 — `page.pdf()` doesn't report a page count directly the way `pdflatex` did, so this happens after rendering instead of during compilation). Overflow *handling* itself is unchanged in design: the user is emailed immediately (same approve/reject mechanism as a `review_gate/` routing, bypassing the Controller's honesty/relevance check since overflow isn't a content question) — see `../CLAUDE.md` for the full decision history. That email step isn't built yet: `write_resume()`/`write_cover_letter()` return `WriteResult(path=None, error=WriteError.OVERFLOW)` on overflow (decided 2026-08-05) — distinct from a bad-JSON or failed-validation response (`WriteError.INVALID_JSON`/`VALIDATION_ERROR`), which is a broken LLM response with no real content and can't route through the review-email design at all (see `write/README.md`).

## Submodules

- `generate.py` — orchestrates `llm/`, `prompts/`, and `write/` for all three calls (resume, cover letter, application answers). See the Orchestration paragraph above.
- `llm/` — Ollama client wrapper. See `llm/README.md`.
- `prompts/` — builds the four prompt strings (one system, three user) fed into `llm/`, each instructing the model to return JSON. See `prompts/README.md`.
- `write/` — parses each call's JSON output and turns it into its final artifact (rendered PDF, or form-field answers handed to `form_automation/`). See `write/README.md`.
- `write/templates/` — the Jinja2 HTML/CSS templates (`resume.html`, `cover_letter.html`, shared `_style.html`/`_macros.html` partials) that replaced the former `resume_template.tex` / `cover_template.tex` LaTeX style shells (decided 2026-08-04/05, see `../CLAUDE.md`). Built; visually mirrors the old LaTeX design (`#2656A6` accent, same header/section layout).

Scratch/prototype code — module boundaries and prompt formats are still settling. See `../CLAUDE.md`.

# tailoring

Generates a per-job resume, cover letter, and free-text/behavioral screening-question answers from `source_of_truth/` facts. Reorders/rephrases/emphasizes only — never adds a fact that isn't in `source_of_truth/`.

**Pipeline role: Application Generator.** Second stage of `Data -> Hybrid Search -> Application Generator -> Application Controller -> Application API`. Runs on postings that cleared `matching/`'s `hybrid_search`, highest `matching_fact_count` first, until the run's submitted-application cap — it has no say in fit or order. Its output goes to `review_gate/` (honesty/relevance check) before anything reaches `form_automation/`.

**Generator input:** the facts that cleared `matching/`'s threshold — `evaluate_posting`'s `matching_facts`, as the result dicts `hybrid_search` returns (`{doc_id, content, ...}` — the prompts read `doc_id` and `content`), gap/screening facts included (this module keeps those out of the resume/cover-letter prompts itself, see below). No separate top-N: older notes' "top-N" meant this set, typically ~5–15 facts, which also bounds the prompt size against `NUM_CTX`. No resolve-by-id step, since each `content` is already the full serialized atomic fact (see `../matching/README.md`'s Types section). The glue passing `matching_facts` into `generate()` isn't written yet.

**Three separate LLM calls:** one Ollama call each for the resume, the cover letter, and free-text/screening-question answers — not one combined call. All three share a system prompt (honesty rules, prompt-injection framing for raw posting text) and differ only in the user-role content. Deterministic screening questions (visa, salary, EEO) skip the LLM entirely, answered directly from `source_of_truth/`.

**Language: Python**, internal module of the shared Python service (see `../README.md`). Local LLM via Ollama, CPU-only (current default: `qwen2.5:14b`, JSON-schema-constrained output, see `llm/README.md`).

Behavioral answers draw on `projects-detail.json` and `general-stories.json` for incident-level material. Known gaps (degree, experience, GPA, sponsorship) are **not** left to search ranking or to the LLM (option (b) and the "raise a gap only if the posting asks" rule, both decided 2026-09-30 — see `../CLAUDE.md`): `generate()` takes `known-gaps.json`'s full list as its own `known_gaps` argument, and `gaps/gaps.py`'s `decide_gaps()` decides in plain code, before any LLM call, which ones the posting asks about. Only those reach the cover-letter call; the decisions (with reasons) land in `GenerateResult.gap_decisions` for the review email. Search still decides fit and picks the facts (`matching_facts`), but facts that aren't fit evidence — exactly the ones `matching/` doesn't count (`matching.matcher.is_fit_fact`): `known_gap:*`, `education` (holds the GPA), `professional_experience`, the `job_preference:*` screening answers, and the logistics preferences (work mode, regions) — are dropped from the resume and cover-letter prompts, so search can't put an unasked-for gap, or "remote preferred" in an on-site letter, back in. One shared definition, not two lists. The application call keeps every fact, since a free-text answer about experience or education still has to be honest. No caching — every answer regenerates fresh.

## Output

**Format: PDF**, via Playwright print-to-PDF. The LLM returns JSON (see `prompts/README.md`); `write_resume()`/`write_cover_letter()` in `write/write.py` take that JSON string directly, validate it against `pydantic` models, fill a Jinja2 HTML template (autoescape handles escaping), and render. The resume fills a fixed structure (one block per project plus summary/skills); the cover letter is freeform prose within a style shell (header, date, greeting, closing).

The application call's `{field_id: answer}` response is handled the same way minus rendering: `parse_application_answers()` (also in `write/write.py`) validates structurally via `pydantic.TypeAdapter(dict[str, str])`, checks the answers against the questions asked (exact `field_id`s, `"not provided"`, `max_length` — see `write/README.md`) and returns `ParseResult(answers, error, flagged)`. `form_automation/` (not built) is the intended consumer of `.answers`.

**One page is a hard constraint** on every generated document — content renders first, free to flow past one page, then the rendered PDF's page count is checked via `pypdf` (Playwright's `page.pdf()` doesn't report a count the way `pdflatex` did). Overflow doesn't get clipped with CSS — that would silently truncate content — it returns `WriteResult(path=..., error=WriteError.OVERFLOW, content=...)` instead, keeping both the file and the parsed text for review. On overflow the user is emailed directly — inline full text, approve/reject — **bypassing the Controller**, since length isn't a content question. The reply is binary: reject (the application ends) or approve (the one-page rule is overridden and it proceeds). Unanswered when the run ends: not submitted, no exclusion, the file deleted; the posting comes back next run. That routing isn't built yet.

## Cover letter rules

The resume fills a fixed template; the cover letter is freeform prose inside a style shell, governed by rules instead:
- **Hard (mechanically enforced):** one page (as above); a gaps paragraph exactly when the posting asks for something a known gap covers — one named mismatch per such gap, never softened or omitted (decided in code, see `gaps/README.md`); every claim traceable to `source_of_truth` (checked by `review_gate/`, not here).
- **Written by code, not the model:** the opening sentence (role and company), the gaps paragraph (the user's own `known-gaps.json` `text` for each applicable gap, word for word), and the closing. The model writes only the "why", the experience paragraph(s), and at most one sentence naming a narrower stack-specific gap — see `write/README.md`'s Cover letter assembly.
- **Soft (prompt guidance only, same as the manual workflow at the repo root):** the model's parts stay short and specific — 1–2 experience paragraphs chosen for this posting; no generic filler; match the posting's tone where it's direct.

## Orchestration

`generate.py`'s `generate(facts, job_posting, profile, questions, known_gaps, output_dir) -> GenerateResult` (`profile` is `profile.json`: its `personal` block fills the headers, its `summary` anchors the resume summary) calls the LLM once per call (no retry on any failure), passes each raw response to `write_resume()`/`write_cover_letter()`/`parse_application_answers()`, and aborts the remaining steps as soon as one fails — an LLM failure, a failed render, or a broken response (`INVALID_JSON`/`VALIDATION_ERROR`) all stop the sequence rather than, say, spending the single Ollama slot on a cover letter for an application whose resume is already dead. `OVERFLOW` does *not* stop it: that content is real and goes to the user for approve/reject. Output files go to `output_dir/<stem>_resume.pdf` / `<stem>_cover_letter.pdf`, where `<stem>` is `filename_stem(job_posting["id"])` — the ID with every character outside `[A-Za-z0-9_-]` encoded reversibly (`:` → `~3a`), since it's outside data and must not be able to escape `output_dir`, and two ids must never share a file (`tracking/` should reuse the same function for its per-application files). `GenerateResult(resume, cover_letter, application, gap_decisions)` distinguishes "never reached" (`None`) from "reached and failed" (a result with `.error` set); `gap_decisions` is filled before any LLM call.

Failures are caught explicitly by type, not with a blanket `except Exception` or implicit `None` checks: `PromptTooLongError` (prompt might not fit `NUM_CTX`, checked before sending) → `WriteError.PROMPT_TOO_LONG` — but each prompt is first shrunk by dropping the lowest-ranked facts until it fits (`fit_facts()`), so this only happens when the posting itself is too big, not because it matched many facts; `OutputTooLongError` (hit `NUM_PREDICT`) → `WriteError.OUTPUT_TOO_LONG`; `OllamaError` (from `llm_ollama()`, see `llm/README.md`) → `WriteError.LLM_FAILURE`; `playwright.async_api.Error`/`pypdf.errors.PyPdfError` during rendering → `WriteError.RENDER_FAILURE`. Anything else propagates as a real exception rather than being absorbed into a result that would look like a normal failure.

Content failures (`INVALID_JSON`, `VALIDATION_ERROR`, `PROMPT_TOO_LONG`, `OUTPUT_TOO_LONG`) mean a permanent exclusion for the posting; infrastructure failures (`LLM_FAILURE`, `RENDER_FAILURE`) mean it comes back next run and the run should stop — see `write/README.md`. When a later step kills the application, PDFs already rendered for it are deleted (their parsed text stays in `.content`). With an empty `questions` list the application call is skipped (`ParseResult(answers={})`) rather than spending a full LLM call on an empty object.

The `questions` list for the application call is supplied by the caller — `generate()` doesn't source it itself; that's `form_automation/`'s job (reading the actual application form), and it doesn't exist yet.

## Submodules

- `generate.py` — orchestrates `llm/`, `prompts/`, and `write/` for all three calls. See Orchestration above.
- `llm/` — Ollama client wrapper. See `llm/README.md`.
- `prompts/` — builds the four prompt strings (one system, three user), each instructing JSON output. See `prompts/README.md`.
- `write/` — parses each call's JSON output into its final artifact (rendered PDF, or form-field answers for `form_automation/`). See `write/README.md`.
- `gaps/` — decides in plain code which known gaps the posting asks about, before any LLM call. See `gaps/README.md`.
- `write/templates/` — Jinja2 HTML/CSS templates (`resume.html`, `cover_letter.html`, shared `_style.html`/`_macros.html` partials), visually mirroring the project's established design (`#2656A6` accent, same header/section layout).

Scratch/prototype code — module boundaries and prompt formats are still settling. See `../CLAUDE.md`.

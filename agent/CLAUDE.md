## Folder structure
- `agent/` holds everything belonging to the automation project, kept separate from the manual cover-letter workflow files at repo root (`cover.tex`, `resume.pdf`, `applications.md`), which are unaffected by this project.
- `agent/source_of_truth/profile.json` is the profile store — the structured, hand-maintained source of truth (education, projects, skills, job preferences, etc.) that the agent will draw from to generate per-job resumes/cover letters and score fit. Built from `resume.pdf`, with any gaps filled in by the user directly (never inferred/guessed). Built and in use.
- `agent/source_of_truth/` is expanding from this single file to several JSON files (decided direction, not yet fully specified beyond these four):
  1. A **projects-detail file** — going deeper per project than the `projects` array in `profile.json`: tech stack, turning points (specific incidents/decisions during development), planning process, structure. Gives the LLM honest incident-level material for project-specific behavioral questions, not just feature-level bullets.
  2. A **general-stories file** (built — see `general-stories.json`) — real anecdotes not scoped to any one project, for behavioral questions the projects-detail file can't answer. Three stories so far: rebuilding a broken study streak through visible progress-tracking (the personal reason for the breaks is deliberately not named — kept private per the user, framed only around the observable behavior); choosing to redo the entire Backend Developer Path in TypeScript for depth rather than because the language was new; and leaning on AI tools for guided-project research, then carrying those concepts into independent projects rather than treating them as one-off exercises.
  3. A **known-gaps file**, hand-maintained by the user directly (not pipeline-generated) — honest, pre-considered phrasing for this candidate's recurring gaps (in-progress distance-learning degree, no professional work experience, GPA 2.6/4.0, needs visa sponsorship). Exists to carry the manual cover-letter workflow's established stance (name gaps directly, never gloss over or hedge them — see the honesty rules in the root `CLAUDE.md`) into the automated pipeline, since a small CPU-only local model is more likely to soften or omit a gap by default, and some pipeline output gets auto-submitted with no human reading it first.
  4. A **preferences file** (decided 2026-07-22, built — see `preferences.json`) — a generalized, shared statement of what roles/locations/stacks this candidate is open to: backend developer primary, fullstack/AI-ML also acceptable; remote preferred, open to Europe/USA/Canada; Go and Python prioritized over TypeScript. Replaces what used to be a per-instance `job_config` filter on the Go orchestrator — since it's now one shared set rather than narrowed per run, it belongs here instead. Feeds `matching/`'s single `hybrid_search(job_posting, source_of_truth)` call. Distinct from the existing `job_preferences` field in `profile.json`, which answers deterministic screening questions (salary, visa, notice period) — `preferences.json` explicitly points back to `profile.json` for those rather than duplicating them.

### Planned folder structure (scaffolded as placeholders — no implementation code exists for any of this)
Mirrors the pipeline modules from the design discussion, one folder per module, each currently just a `README.md` stub restating its purpose:
- `agent/source_of_truth/` — profile store. Done, in use.
- `agent/sourcing/` — pulls job listings from ATS-backed career pages only (v1 scope excludes LinkedIn/Glassdoor/JobLeads). Per-ATS adapters (Greenhouse, Lever, Ashby, Workday, etc.), shared with `form_automation/` where possible since both need to know the same ATS's structure.
- `agent/matching/` — fit-scoring: job description + profile store → a match-strength score (requirements diffed against structured profile-store fields, not LLM self-reported confidence) + reasoning.
- `agent/tailoring/` — generates a per-job resume variant and cover letter from profile-store facts. Reorders/rephrases/emphasizes only — never adds a fact not present in the profile store.
- `agent/form_automation/` — per-ATS-type form-filling (not per-company). Reads a form's fields, maps them to the profile store, fills them; free-text questions get routed to an LLM call with the job description as context.
- `agent/tracking/` — state store logging what was applied to, when, status, and the generated materials, to avoid duplicates and support follow-up. Storage format not yet decided.
- `agent/review_gate/` — houses the **Application Controller** (decided 2026-07-22): a second LLM, distinct from `tailoring/`'s generator, that checks the generator's output against `source_of_truth` (honesty) and the job posting (relevance) before anything gets submitted. Any failure on either check — honesty or relevance, no severity distinction — routes to human review. A user-maintained override list (always review certain roles/companies regardless of the check) still applies independently. Plus outbound notifications for anything queued for review.

Not yet decided: where generated per-job artifacts (tailored resume/cover letter) physically land — written to disk per application, or only ever stored in the tracking store. The folders existing now does not resolve this — check with the user before writing actual implementation code into any of them.

## Architecture (decided, still design-only — no code written)

**Deployment model:** a local k8s distro (k3s/minikube-style) running on the user's own computer — not a cloud-hosted cluster. One Go binary, run as multiple configured orchestrator instances, potentially several running simultaneously — one instance per ATS target (Greenhouse, Lever, etc.), not per module and not per job board (LinkedIn/Glassdoor stay out of v1 scope). Each instance is configured with which ATS to target and a run-duration; it polls that ATS repeatedly, then times out and stops. Role/location/tech filtering is no longer part of instance config (decided 2026-07-22) — that fit decision now happens entirely in `matching/`, against a generalized preference set shared in `source_of_truth/` (see Matching approach below). The user starts/restarts instances manually and reads the end-of-run report afterward — this is not a fully hands-off, zero-touch system.

**Tech stack — three languages, three shared singleton services, not per-instance:**
- **Go** — orchestrator. Thin: each per-ATS instance's whole job is bridging the Python service's generated output (tailored resume/cover letter, form-field answers) to the TypeScript form-filling service, and creating/finalizing the application. Go does not own pipeline sequencing, tracking-store writes, or review-gate email triggering — those are internal to Python.
- **Python** — one shared service (not one per ATS instance) that internally owns `sourcing/`, `matching/`, `tailoring/`, `tracking/`, and `review_gate/` as modules calling each other directly. Hosts local LLM inference via **Ollama, CPU-only (no GPU available)**, which caps realistic model size to roughly 7-8B quantized for reasonable latency. The LLM's job is constrained to organizing/formatting resume and cover-letter content and answering form fields strictly from `source_of_truth/` — never hallucinating facts not present there, same principle as the honesty rules in the root `CLAUDE.md`.
- **TypeScript** — one shared service (not one per ATS instance) handling `form_automation/` (likely browser automation for JS-heavy application forms).

**Pipeline (decided 2026-07-22):** `Data -> Hybrid Search -> Application Generator -> Application Controller -> Application API`, mapping onto the folders above — `matching/` runs Hybrid Search (deterministic, single-call, see Matching approach below); `tailoring/` is the Application Generator, running unconditionally on every posting that clears the match step; `review_gate/` is the Application Controller, checking the generator's output for honesty and relevance before anything ships; `form_automation/` (bridged through the Go orchestrator) is the Application API — the actual submission call to the ATS, firing only once the Controller (or the user, via the review email) approves.

**Screening questions:** deterministic, always-the-same-answer questions (work authorization, visa sponsorship, salary, notice period, language, EEO/legal boilerplate) are structured fields directly in `source_of_truth/` (`job_preferences` plus `eeo` fields, built 2026-07-22 — distinct from the newly separate `source_of_truth/preferences.json` used by `matching/`, see Matching approach below) — the LLM is never involved in answering these. The LLM only handles the generative side: resume tailoring, cover letters, and free-text/behavioral questions ("tell me about a time you solved a bug"), always generated from `source_of_truth/` content, never invented. No answer caching for now — every generated answer is produced fresh each time, not reused or adapted from a past answer (revisit if regeneration cost/consistency becomes a problem later).

**Matching approach (updated 2026-07-22, single-call design supersedes the two-stage gate this replaces):** fully deterministic, no LLM in the fit decision at all. One call, `hybrid_search(job_posting, source_of_truth)`, per posting — no chaining, no separate `job_config` stage. `job_config` is reduced to **ATS only** (which career-page adapter/instance polls) — a sourcing/orchestrator routing concern, never fed into `hybrid_search`. The role/location/tech preferences that used to live in per-instance `job_config` (e.g. "backend developer, Germany" vs. "fullstack developer, Sweden") are **generalized** into one preference set shared across every instance — since they're no longer narrowed per run, they fit inside the single shared, read-only `source_of_truth` without breaking its "no per-instance customization" rule. Tentatively a new file, `source_of_truth/preferences.json` (see folder structure above). `hybrid_search` combines embedding search (sentence-transformers, CPU-only, cosine similarity) with keyword search (BM25) via RRF fusion — no structured field-diff. No caching layer — `job_posting` and `source_of_truth` embeddings are recomputed on every comparison (documents aren't large enough to justify caching). **Soft/inferred requirements are dropped** (e.g. "strong communication skills" that don't reduce to a checkable field) — an accepted tradeoff for now, not arbitrated by an LLM or anything else. Everything that passes goes to `tailoring/` unconditionally, where the LLM runs purely to generate application materials — it has no vote on fit. **Corpus/query direction and granularity (decided 2026-07-22):** `source_of_truth` is the indexed corpus, `job_posting` is the query string, and the corpus is built at one `Document` per atomic fact (every skill, project, known-gap, story, and preference item gets its own `Document`) — so the ranked output is your own facts scored against a given posting, not the posting's requirements scored against your profile. **Pass/fail signal (decided 2026-07-22):** use `rrf_search`'s fused `rrf_score` as-is, keeping both BM25 and semantic search combined via RRF exactly as already built — a raw semantic-similarity score would be more precise but requires code changes to carry it through fusion (currently dropped in `hybrid_search.py`'s final result assembly), and that precision was explicitly declined in favor of using search as it already exists. Known, accepted imprecision: `rrf_score` is rank-based, not similarity-magnitude-based, so a corpus's top-ranked fact scores similarly whether it's a strong match or just the least-bad option. **Threshold rule (decided 2026-07-22, empirically corrected same day):** a posting passes when at least 4 distinct facts from `source_of_truth` score `rrf_score` ≥ 0.028 against it. The original guess (0.026) was tested end-to-end and failed to discriminate — a mismatched sales-manager test posting also cleared it (12 facts, versus 13 for a genuinely relevant backend posting). 0.028 is where the two test postings actually separate (9 facts vs. 2). Sourcing needs no pre-filter beyond ATS — role/location/tech fit is fully decided at this matching step. Document construction is built: `matching/document_builder/document_builder.py` turns the five `source_of_truth` files into one `Document` per atomic fact (`json.dumps` per fact, no templating) and job postings into query strings the same way (`json.dumps` on the posting JSON). Matching's design is now fully settled end-to-end; only recalibrating the threshold against real data remains. See `matching/README.md`.

**Types (decided 2026-07-22):** `job_posting` and `source_of_truth` entries reduce to the same simple shape for search purposes — `Document(id, content)`, a stable id plus flattened text — so `hybrid_search` can operate on both uniformly (`job_config` no longer participates in search — see Matching approach above). `hybrid_search` returns `id` plus the matched `Document` itself, not bare ids. The richer structured record behind each `id` (the real ATS listing JSON, or the structured `source_of_truth` JSON) is resolved separately, by that same `id`, and it's *that* structured version — not the flattened `Document` — that gets handed to the Application Generator, since the LLM benefits from real structure that the flattened search text discards.

**Tracking:** must be a single store shared across all concurrently-running Go orchestrator instances (reads *and* writes), not local per-instance state — otherwise two instances (e.g. Greenhouse + Lever running at once) could double-apply to the same company/role. Storage format not yet decided. `source_of_truth/profile.json` stays read-only and shared by contrast — the pipeline never writes to it.

**Review gate / Application Controller (updated 2026-07-22):** routing to human review is no longer a numeric confidence threshold. A second LLM (the Application Controller, distinct from the Application Generator in `tailoring/` — whether it runs on the same local CPU-only Ollama instance or a separate model/service is not yet decided) checks the generator's output against `source_of_truth` (honesty — is every claim traceable to a real fact) and against the job posting (relevance — does the answer actually address what was asked). Any failure on either check — no distinction in severity between a honesty miss and a relevance miss — routes to human review; passing both sends the application straight to Application API for submission. A user-maintained override list (certain roles/companies always reviewed regardless of the check) still applies on top of this.

No dashboard. Push notification via **email** with clickable approve/reject links fires immediately when something routes to review; a separate end-of-run report (submitted, matched-but-not-submitted, skipped, errors) is generated when an instance times out, for the user to read at their own pace. If the user doesn't respond before the instance's run ends, the item **defaults to reject**.

The review email shows the **full generated package inline** in the body — resume text, cover letter text, filled form field answers — not summarized and not as attachments (attachments are phone friction). Driving reasoning: missing a bad generation in a too-short email is a worse failure mode than a long email, so it errs toward showing everything. It also includes a **log/report-style breakdown of why that specific application was routed to review** (the Application Controller's honesty/relevance verdict and reasoning, or which manual-override rule fired), distinct from the separate end-of-run report that summarizes a whole container run.

**Sending mechanism (decided):** a dedicated Gmail account created specifically for this app sends the review-request emails to the user's personal address, via Gmail's own SMTP/API. Needs no inbound reachability — any container with outbound internet access can send.

**Receiving mechanism (decided):** one extra tap is acceptable — the link opens a confirm page rather than firing the action on a bare GET (bare links risk being auto-triggered by email security scanners/prefetchers before the user ever opens the email). Reachability must work from anywhere, in a normal browser, with no special app installed — this rules out Tailscale (private mesh, requires the Tailscale app on the device) in favor of **Cloudflare Tunnel**: a real public HTTPS URL, free tunnel service, but requires a domain the user controls (~$10-15/year — not yet owned, needs registering) and the link itself becomes a bearer credential needing its own token-based protection since the endpoint is genuinely public.

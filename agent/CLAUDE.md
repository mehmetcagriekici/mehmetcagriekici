## Folder structure
- `agent/` holds everything belonging to the automation project, kept separate from the manual cover-letter workflow files at repo root (`cover.tex`, `resume.pdf`, `applications.md`), which are unaffected by this project.
- `agent/source_of_truth/profile.json` is the profile store — the structured, hand-maintained source of truth (education, projects, skills, job preferences, etc.) that the agent will draw from to generate per-job resumes/cover letters and score fit. Built from `resume.pdf`, with any gaps filled in by the user directly (never inferred/guessed). Built and in use.
- `agent/source_of_truth/` is expanding from this single file to several JSON files (decided direction, not yet fully specified beyond these four):
  1. A **projects-detail file** (built — see `projects-detail.json`; covers 7 of 8 projects, Message Notification Router pending) — going deeper per project than the `projects` array in `profile.json`: tech stack, turning points (specific incidents/decisions during development), planning process, structure. Gives the LLM honest incident-level material for project-specific behavioral questions, not just feature-level bullets.
  2. A **general-stories file** (built — see `general-stories.json`) — real anecdotes not scoped to any one project, for behavioral questions the projects-detail file can't answer. Three stories so far: rebuilding a broken study streak through visible progress-tracking (the personal reason for the breaks is deliberately not named — kept private per the user, framed only around the observable behavior); choosing to redo the entire Backend Developer Path in TypeScript for depth rather than because the language was new; and leaning on AI tools for guided-project research, then carrying those concepts into independent projects rather than treating them as one-off exercises.
  3. A **known-gaps file**, hand-maintained by the user directly (not pipeline-generated) — honest, pre-considered phrasing for this candidate's recurring gaps (in-progress distance-learning degree, no professional work experience, GPA 2.6/4.0, needs visa sponsorship). Exists to carry the manual cover-letter workflow's established stance (name gaps directly, never gloss over or hedge them — see the honesty rules in the root `CLAUDE.md`) into the automated pipeline, since a small CPU-only local model is more likely to soften or omit a gap by default, and some pipeline output gets auto-submitted with no human reading it first.
  4. A **preferences file** (decided 2026-07-22, built — see `preferences.json`) — a generalized, shared statement of what roles/locations/stacks this candidate is open to: backend developer primary, fullstack/AI-ML also acceptable; remote preferred, open to Europe/USA/Canada; Go and Python prioritized over TypeScript. Replaces what used to be a per-instance `job_config` filter on the Go orchestrator — since it's now one shared set rather than narrowed per run, it belongs here instead. Feeds `matching/`'s single `hybrid_search(job_posting, source_of_truth)` call. Distinct from the existing `job_preferences` field in `profile.json`, which answers deterministic screening questions (salary, visa, notice period) — `preferences.json` explicitly points back to `profile.json` for those rather than duplicating them.

### Folder structure
Mirrors the pipeline modules from the design discussion, one folder per module. **Built (code exists, committed):** `source_of_truth/` (data), `matching/`, `tailoring/`. **Design only (just a `README.md`, no code):** `sourcing/`, `form_automation/`, `tracking/`, `review_gate/`.
- `agent/source_of_truth/` — profile store. Done, in use.
- `agent/sourcing/` — pulls job listings from ATS-backed career pages only (v1 scope excludes LinkedIn/Glassdoor/JobLeads). Per-ATS adapters (Greenhouse, Lever, Ashby, Workday, etc.), shared with `form_automation/` where possible since both need to know the same ATS's structure. **Company list (decided 2026-10-06):** ATS public APIs are per-company (Greenhouse `boards/{company}/jobs`, Lever `postings/{company}`, Ashby `job-board/{company}`; Workday has no public API at all) — there is no "everything on Greenhouse" feed, so an instance polls a list of companies, not an ATS as a whole. v1: a **hand-maintained list in its own file under `sourcing/`**, shared by all instances (each reads the entries for its own ATS). **Format (decided 2026-10-07): JSON** (matching `source_of_truth/`), an array of `{ats, board, enabled, note}` — `board` is the board name from the ATS URL (renamed from `company` 2026-10-07, so `company` always means the display name), `enabled: false` pauses a company without deleting it, `note` is a free-text reminder the pipeline ignores. **No display-name field:** the company's real name (the normalized posting's `company`, used in the cover letter's greeting) comes from the ATS response where the ATS provides one (to be confirmed per adapter — not every ATS's postings endpoint is known to include it; a board-level endpoint or the board name itself is the fallback). Automatic company discovery (e.g. search-engine queries for board URLs) is deferred as an explicit later phase — search-engine scraping carries the same ToS/fragility concerns that kept LinkedIn out of v1. **No `requirements` field in the normalized posting (decided 2026-10-07):** real ATSs don't deliver a requirements list (Greenhouse gives one HTML blob; Lever's sections have free-text headings), and guessing the requirements section by heading would fail silently — a miss means "no years requirement found", so the experience gap wouldn't be raised. Instead sourcing only guarantees `description` is plain text with each HTML bullet on its own line, and `tailoring/gaps/gaps.py`'s years rule scans every line of the description, prose lines split into sentences (done 2026-10-07 — before, it read only a `requirements` list and went silent on normalized postings; it still also reads `requirements`/`nice_to_have` for the synthetic fixtures). Accepted cost: a "5 years" in e.g. a benefits bullet can raise the experience gap unnecessarily — the safe direction under the raise-when-ambiguous rule. **Normalized posting shape (decided 2026-10-07):** `id` (namespaced `{ats}:{board}:{ats_id}`, so numeric Greenhouse ids can't collide with other ATSs' in `tracking/`'s id-keyed filenames), `ats`, `board` (the URL slug), `company` (the display name), `title`, `location` (free text), `workplace_type` (`remote`/`hybrid`/`onsite`/`unknown` — real values from Lever/Ashby, `unknown` for Greenhouse, where the visa rule falls back to location text), `description`, `url`, `posted_at`, plus **`raw`: the untouched ATS response**, kept so a rule misfiring on a real posting can be debugged against what the ATS actually sent. **Consumers read named content fields, never the whole dict (decided 2026-10-07):** `matching/`'s query, `tailoring/`'s prompts, and the gap rules all go through `posting_content()` (`matching/document_builder/`) — `title`, `company`, `location`, `workplace_type`, `employment_type`, `description` (plus the fixtures' `requirements`/`nice_to_have`) — so `raw`, ids, urls, dates and salary are stored but never sent into a search, a prompt, or a keyword rule. **Stale-posting filter (decided 2026-10-07):** sourcing drops postings older than **30 days** — the one filter sourcing applies (a freshness check, not a fit decision; role/location/tech fit stays entirely in `matching/`). Age comes from the first-published date where the ATS exposes one, falling back to the updated date (some companies bump old postings' updated date without changing them, which makes ghost listings look fresh); each adapter's actual date fields get confirmed when it's built. Dropped postings are listed in the end-of-run report as "skipped (stale)", never silently discarded. **Pacing and errors (decided 2026-10-07):** a fixed ~1-2 s delay between company boards (20-50 requests per run makes anything smarter unnecessary). A board that fails to fetch (404 from a renamed/moved board, timeout, etc.) is skipped and reported ("board fetch failed: acme (404)"); a posting the normalizer can't handle (e.g. missing title) is skipped and reported while the rest of that board proceeds. **No auto-disable:** the pipeline never writes to the hand-maintained company list — a repeating failure in the report is the user's cue to fix or disable the entry. **Implementation work this design implies:** done — `tailoring/gaps/gaps.py`'s years rule scans description lines; `posting_content()` limits what consumers read. Not yet done: the four `matching/fixtures/postings/` fixtures move to the normalized shape (no `requirements` array, bullets as description lines); the matching threshold is recalibrated after that — ideally against real postings fetched by the first adapter, since the fixture shape change alters the search text; `tracking/` gains exclusion records; the ranking + submitted-application cap live in whatever runs the pipeline (not yet written).
- `agent/matching/` — fit-scoring: deterministic hybrid search (BM25 + embeddings, RRF-fused) of the posting against `source_of_truth` facts — a pass/fail verdict plus `matching_fact_count`, which ranks matched postings (see Matching approach below). Built.
- `agent/tailoring/` — generates a per-job resume variant and cover letter from profile-store facts. Reorders/rephrases/emphasizes only — never adds a fact not present in the profile store. Output format is **PDF** (decided 2026-07-26). Generated artifacts are **written to disk per application** (decided 2026-07-26 — resolves the prior open question below). **The LLM fills a fixed template rather than generating freeform** (decided 2026-07-26): the resume side reduces to a repeatable structural pattern (one block per `projects[]` entry plus a summary/skills section) that a template can fill mechanically — distinct from the cover letter's freeform prose (see below). **Rendering: Playwright print-to-PDF (decided 2026-08-04, replaces an earlier LaTeX/`pdflatex` design that was fully superseded before any of it shipped)** — `write/write.py` renders HTML/CSS to PDF via a real, actively-maintained headless Chromium engine, chosen over the `wkhtmltopdf`/`pdfkit` alternative (rejected: unmaintained project, old QtWebKit engine, worse page-break precision, packaging headaches in containers). This is scoped to the agent pipeline only — the manual cover-letter workflow at repo root stays on LaTeX (`cover.tex`, governed by the root `CLAUDE.md`), unaffected by this choice. **Templates built (decided 2026-08-05): Jinja2 with autoescape**, chosen over manual string building specifically so escaping (the deterministic-code job LaTeX-escaping used to fill) is handled by the templating engine itself rather than relying on every interpolated field being escaped by hand. `write/templates/resume.html` and `cover_letter.html` (plus shared `_style.html`/`_macros.html` partials) mirror the old LaTeX templates' visual design — same `#2656A6` accent, same header/section layout, fed by `profile.json`'s `personal` block for contact info. `write_resume()`/`write_cover_letter()` in `write/write.py` take the `RESUME_SCHEMA`/`COVER_LETTER_SCHEMA`-shaped JSON directly (see `prompts/README.md`) and render it; the old `resume_template.tex`/`cover_template.tex` LaTeX shells are deleted, fully superseded. **One page is a hard constraint on every generated resume** (decided 2026-07-26), not just a property of a single snapshot — since `tailoring/` will swap in different per-job LLM-generated content each time (different summary/project text per posting), fitting one page has to hold across that variation. **Enforcement mechanism (decided 2026-08-05, resolves the Playwright-era open question): render first with content left free to flow past one page, then check the rendered PDF's page count via `pypdf`** — Playwright's `page.pdf()` doesn't report a page count directly the way `pdflatex` did, so the check happens after rendering instead of during compilation. An earlier draft tried clipping to one page with CSS `overflow: hidden` instead — rejected, since it silently truncates content past the page boundary rather than surfacing the failure, and a resume cut off mid-sentence must never ship unnoticed. **On overflow, it emails the user immediately (decided 2026-07-27)**, the same way a Controller-routed honesty/relevance failure does (inline full text, approve/reject link) — and it **bypasses the Controller's honesty/relevance check** (decided 2026-07-27), since the user's own review is the only gate needed for what was never a content question. The user's reply is binary: **reject** (application dies here) or **approve for continuing** (overrides the one-page constraint and the pipeline proceeds) — mirroring the existing review-email approve/reject mechanism rather than inventing a new one. **Unanswered when the run ends (decided 2026-10-07):** treated like a timed-out review — not submitted, no exclusion, the file deleted (the application has concluded); the posting comes back in a later run. A review link tapped after its run has ended (overflow or Controller review) opens a page saying it expired and the posting will come back, rather than acting. That email-routing step itself isn't built yet: `write_resume()`/`write_cover_letter()` currently return a `WriteResult` with `error=OVERFLOW`, still carrying the rendered file's path and the parsed content, for a caller (not yet written) to act on. Deployment implication of the Playwright pivot: the container image needs a `playwright install --with-deps chromium` build step and the `fonts-liberation` package (the templates pin Liberation Sans so the one-page check gives the same page count on every machine) — documented in `README.md`'s Python service setup section; no Dockerfile exists yet.

**Cover letter (decided 2026-07-26): rules-based, not a fill-in template like the resume.** The cover letter's style shell (header block, date, greeting, closing, same accent-color styling as root `cover.tex`) now has its HTML/CSS equivalent built (`write/templates/cover_letter.html`, see the Playwright pivot above) and carries no per-job body content, since unlike the resume's repeatable per-project block, a cover letter's body doesn't reduce to a repeatable structural pattern; it's genuinely freeform prose generated per job. Two kinds of rules apply instead:
- **Hard, mechanically-enforced rules:** one page (same render-then-count-pages mechanism as the resume — see above; overflow emails the user directly, bypassing the Controller); a gaps paragraph is required **whenever the posting asks for something a known gap covers** — one named mismatch per such gap, never softened or omitted, carrying forward the root `CLAUDE.md` honesty rule into the automated pipeline. **Revised 2026-09-30 (supersedes "structurally required, never optional"): if a posting doesn't ask, the gap is not raised** — a posting that asks about none of them gets no gaps paragraph at all. **Considered and not chosen (2026-09-30):** post-LLM string checks on the generated text (e.g. scanning for banned phrases like "proven"/"production"/"experienced") — the user chose a bigger model plus moving decidable rules into code *before* the LLM, with anything left for `review_gate/`. An intermediate approach, a `gap_decisions` field where the model judged each gap's rule itself before writing, was built and replaced the same day by the code rules below. Which gaps apply is decided in plain code before the LLM runs (`tailoring/gaps/gaps.py`: degree only if the posting mentions one, GPA only if asked, experience only if years/professional experience is asked for, visa unless the role is fully remote from Turkey or located there — ambiguity resolves toward raising), not by the LLM, which misapplied these rules about half the time; every claim traceable to `source_of_truth` (existing global rule, actually caught by `review_gate/`'s honesty check, not the loop).
- **Soft, style-only rules (not mechanically checked, same guidance the manual workflow has already used across every letter sent so far):** 3-4 short paragraphs (opening naming the role and why writing, 1-2 experience paragraphs selected for relevance to *this* posting, the gaps paragraph when any gap applies, a brief close); no generic-enthusiasm filler ("I am a great fit for..."); match the tone of the posting where the posting itself is direct; address the specific role/company by name.
- `agent/form_automation/` — per-ATS-type form-filling (not per-company). Reads a form's fields, maps them to the profile store, fills them; free-text questions get routed to an LLM call with the job description as context.
- `agent/tracking/` — state store logging what was applied to, when, status, and the generated materials, to avoid duplicates and support follow-up. **Must store the full generated resume/cover-letter text (decided 2026-07-27)**, not just metadata — resolves a gap found when working through the disk-cleanup decision below: applications that pass the Controller without routing to review never have their content shown anywhere else (the review email is the only other place full text appears, and it only fires on review), so once the on-disk file is deleted, `tracking/` is the sole surviving record of what was actually submitted. **Storage format (decided 2026-07-27): plain JSON files for now, no database** — the user is comfortable with PostgreSQL and may stand up a local instance later, but that's an explicit future migration, not the v1 design. **Double-apply race is a non-issue (decided 2026-07-27):** the concurrency concern from the architecture note below (multiple Go orchestrator instances writing at once) doesn't actually apply here, since Python runs as one shared singleton service — every instance's writes funnel through that single process, which serializes them naturally within a run, rather than needing multi-writer coordination at the storage layer. **Granularity (decided 2026-07-27): one JSON file per application**, not one running log/array file for the whole store — chosen as the simpler starting option, consistent with the per-application resume/cover-letter files already being written to disk. Duplicate-detection will need to query across all of these per-application files rather than scanning a single one; not treated as a concern for now. **Duplicate key (decided 2026-07-27): job posting ID as the primary match, with a company+role fallback.** The job posting ID is also the filename of each per-application JSON file (decided 2026-07-27) — primary dedup is a plain file-existence check; the company+role fallback requires an actual scan across files, since it only kicks in when the ID lookup misses. ID-match is an explicit, acknowledged assumption — it only catches a repost if the ATS keeps the same ID on re-listing, which isn't guaranteed to hold uniformly across the v1 ATS set (Greenhouse, Lever, Ashby, Workday); the company+role fallback exists specifically to catch the cases where a repost gets a fresh ID instead. **Pipeline goal (stated by the user 2026-10-07): not to apply to every possible job, but to the best-matching ones — 10–50 applications per week is satisfying.** Consequences decided the same day: **matched postings are ranked by `matching_fact_count`** (facts scoring ≥ the threshold — already returned by `evaluate_posting`), and generation always takes the highest-ranked posting next, instead of processing in fetch order; **runs are capped by application count**, not only by run-duration; and **failed, broken, or rejected postings must never come back** in a later poll or run. Mechanism (decided 2026-10-07): a **minimal exclusion record in `tracking/`** — posting id, company + role, reason (failed / broken / rejected by the Controller / rejected by the user), date; no generated text, so it isn't a full application record. It lives in `tracking/` because the duplicate check already runs there right after sourcing and before matching, so excluded postings are dropped by the same lookup at no extra cost. **Exclusions are permanent** — no expiry. **But only content failures exclude (decided 2026-10-07):** the model produced bad output for this posting (`INVALID_JSON`, `VALIDATION_ERROR`), its prompt can't fit (`PROMPT_TOO_LONG`), the Controller rejected it, or the user did. **Infrastructure failures (`LLM_FAILURE` — Ollama down, unreachable, timing out — and `RENDER_FAILURE`) write no exclusion**: the posting is fine and comes back next run, and the runner should **stop the run** on one rather than keep failing through its best-ranked postings. Found in review: one Ollama outage, or a code bug disguised as an Ollama error (a shared client failed on the second `asyncio.run()`, since fixed), would otherwise have permanently excluded every top match in a single run. `tailoring/write/write.py` defines the two sets (`CONTENT_FAILURES`, `INFRASTRUCTURE_FAILURES`). **The run cap counts submitted applications only** — postings routed to review don't count until approved and submitted. **Timed-out reviews are not exclusions (decided 2026-10-07):** a review left unanswered when the run ends still defaults to reject (nothing is submitted), but writes no exclusion record — so the posting can come back in a later run with a fresh review email. Only an explicit user reject, a Controller rejection, or a generation failure/broken response excludes forever. Without this, unanswered reviews would have become permanent exclusions (reviews don't count toward the cap, so they can pile up within a run), silently losing exactly the borderline postings worth a second look. **Fallback matching logic (decided 2026-07-27): simple normalization, not fuzzy matching or an LLM call** — lowercase + trim only, no stemming/suffix-stripping/token-level comparison. Deliberately minimal so it doesn't lose information (e.g. "Software Engineer" vs. "Software Engineer II" stay distinct rather than collapsing into the same bucket), and keeps dedup fully deterministic — no LLM involved, consistent with `matching/`'s existing stance of not spending the CPU-only local model on decisions that can be resolved by plain logic.
- `agent/review_gate/` — houses the **Application Controller** (decided 2026-07-22): a second LLM, distinct from `tailoring/`'s generator, that checks the generator's output against `source_of_truth` (honesty) and the job posting (relevance) before anything gets submitted. Any failure on either check — honesty or relevance, no severity distinction — routes to human review. A user-maintained override list (always review certain roles/companies regardless of the check) still applies independently. Plus outbound notifications for anything queued for review.

Generated per-job artifacts (tailored resume/cover letter) physically land on disk per application (decided 2026-07-26) — not only in the tracking store. **Disk copies are deleted once that application's process concludes (decided 2026-07-27)** — create, use (compile/attach/submit), delete, so `tailoring/`'s working files don't accumulate indefinitely. Safe only because `tracking/` now persists the full text first (see above); without that write, deletion on the no-review-needed path would destroy the only record of what was submitted. "Concludes" means sent (submitted via Application API), rejected (by the Controller or the user, via review), or — since a one-page overflow now also emails the user directly (revised 2026-07-27, see above) — answered: on overflow the file is kept and deletion waits until the user replies reject or approve-for-continuing, same as a review-routed rejection (decided 2026-07-27). For the design-only folders, a folder existing doesn't mean any implementation exists — check with the user before writing implementation code into any of them (and per the no-code rule above, into the built ones too).

## Architecture (decided; `matching/` and `tailoring/` built, the rest design-only)

**Deployment model:** a local k8s distro (k3s/minikube-style) running on the user's own computer — not a cloud-hosted cluster. One Go binary, run as multiple configured orchestrator instances, potentially several running simultaneously — one instance per ATS target (Greenhouse, Lever, etc.), not per module and not per job board (LinkedIn/Glassdoor stay out of v1 scope). Each instance is configured with which ATS to target, a run-duration, and an application cap. **Run shape (decided 2026-10-07, resolves the open "what does a run mean" question from 2026-07-21):** one fetch per run — at start, the instance fetches every listed company's board once, drops stale postings and duplicates/exclusions, runs matching, ranks the matches by `matching_fact_count`, then generates from the top down until either the submitted-application cap or the run-duration is reached. No re-fetching mid-run: at ~1 hour of generation per application on the 14B, discovery isn't the bottleneck. **Python owns the run loop (decided 2026-10-07):** the Go instance starts a run by passing `{ats, run_duration, application_cap}` to Python; Python does fetch → filter → match → rank → generate; Go bridges each generated application to the TypeScript form service and reports each submission's result back, so Python can count submissions toward the cap — consistent with Go owning no pipeline sequencing. Matched postings not reached before the run ends have no record, so they simply come back next run and get re-ranked with whatever's new. Role/location/tech filtering is no longer part of instance config (decided 2026-07-22) — that fit decision now happens entirely in `matching/`, against a generalized preference set shared in `source_of_truth/` (see Matching approach below). The user starts/restarts instances manually and reads the end-of-run report afterward — this is not a fully hands-off, zero-touch system.

**Tech stack — three languages, three shared singleton services, not per-instance:**
- **Go** — orchestrator. Thin: each per-ATS instance's whole job is bridging the Python service's generated output (tailored resume/cover letter, form-field answers) to the TypeScript form-filling service, and creating/finalizing the application. Go does not own pipeline sequencing, tracking-store writes, or review-gate email triggering — those are internal to Python.
- **Python** — one shared service (not one per ATS instance) that internally owns `sourcing/`, `matching/`, `tailoring/`, `tracking/`, and `review_gate/` as modules calling each other directly. Hosts local LLM inference via **Ollama, CPU-only (no GPU available)**, — the default generator model is `qwen2.5:14b` (upgraded 2026-09-30 from the 7B after it ignored prompt-only honesty rules about half the time; ~1 hour of generation per application, accepted since slow is fine for this pipeline). The LLM's job is constrained to organizing/formatting resume and cover-letter content and answering form fields strictly from `source_of_truth/` — never hallucinating facts not present there, same principle as the honesty rules in the root `CLAUDE.md`.
- **TypeScript** — one shared service (not one per ATS instance) handling `form_automation/` (likely browser automation for JS-heavy application forms).

**Pipeline (decided 2026-07-22):** `Data -> Hybrid Search -> Application Generator -> Application Controller -> Application API`, mapping onto the folders above — `matching/` runs Hybrid Search (deterministic, single-call, see Matching approach below); `tailoring/` is the Application Generator, running on matched postings in rank order (highest `matching_fact_count` first) until the run's submitted-application cap or run-duration is reached — see the run shape under Deployment model; `review_gate/` is the Application Controller, checking the generator's output for honesty and relevance before anything ships; `form_automation/` (bridged through the Go orchestrator) is the Application API — the actual submission call to the ATS, firing only once the Controller (or the user, via the review email) approves. **Duplicate check against `tracking/` happens right after `sourcing/`, before `matching/` (decided 2026-07-27)** — a posting already applied to (by job posting ID or the company+role fallback, see `agent/tracking/` above) is dropped before it burns a `hybrid_search` call, not filtered later in the pipeline.

**Prompt injection defense (decided 2026-07-26):** job posting text is attacker-controlled and reaches two LLM calls — the Application Generator (`tailoring/`) and the Application Controller (`review_gate/`'s relevance check, which also reads the raw posting) — so a single shared defense covers both rather than each module inventing its own; `matching/`'s `hybrid_search` needs no such defense since it's fully deterministic, no LLM in the fit decision. The defense is **structural, not a separate detection/scan step**: job posting text is wrapped/framed like a system-prompt boundary in both LLM calls, explicitly labeled as untrusted data rather than instructions. **The boundary itself is protected (fixed 2026-10-07):** `<` and `>` in posting text are escaped (`\u003c`/`\u003e` inside the posting's JSON, HTML entities in plain-text spots), so a posting containing `</job_posting>` can't close the tag early and pose as prompt structure — `json.dumps` alone didn't escape them. Application-form questions (`<questions>`) and posting requirements quoted in the gaps block get the same treatment, and the system prompt labels all three as untrusted. There is no explicit "injection detected" event, no log entry, and no human-review trigger for it — a successfully-framed injection attempt is simply inert (the LLM never treats embedded text as a command it should follow), and the pipeline proceeds normally as if the posting were clean.

**Screening questions:** deterministic, always-the-same-answer questions (work authorization, visa sponsorship, salary, notice period, language, EEO/legal boilerplate) are structured fields directly in `source_of_truth/` (`job_preferences` plus `eeo` fields, built 2026-07-22 — distinct from the newly separate `source_of_truth/preferences.json` used by `matching/`, see Matching approach below) — the LLM is never involved in answering these. The LLM only handles the generative side: resume tailoring, cover letters, and free-text/behavioral questions ("tell me about a time you solved a bug"), always generated from `source_of_truth/` content, never invented. No answer caching for now — every generated answer is produced fresh each time, not reused or adapted from a past answer (revisit if regeneration cost/consistency becomes a problem later).

**Matching approach (updated 2026-07-22, single-call design supersedes the two-stage gate this replaces):** fully deterministic, no LLM in the fit decision at all. One call, `hybrid_search(job_posting, source_of_truth)`, per posting — no chaining, no separate `job_config` stage. `job_config` is reduced to **ATS only** (which career-page adapter/instance polls) — a sourcing/orchestrator routing concern, never fed into `hybrid_search`. The role/location/tech preferences that used to live in per-instance `job_config` (e.g. "backend developer, Germany" vs. "fullstack developer, Sweden") are **generalized** into one preference set shared across every instance — since they're no longer narrowed per run, they fit inside the single shared, read-only `source_of_truth` without breaking its "no per-instance customization" rule. Tentatively a new file, `source_of_truth/preferences.json` (see folder structure above). `hybrid_search` combines embedding search (sentence-transformers, CPU-only, cosine similarity) with keyword search (BM25) via RRF fusion — no structured field-diff. No caching layer — `job_posting` and `source_of_truth` embeddings are recomputed on every comparison (documents aren't large enough to justify caching). **Soft/inferred requirements are dropped** (e.g. "strong communication skills" that don't reduce to a checkable field) — an accepted tradeoff for now, not arbitrated by an LLM or anything else. Passing postings go to `tailoring/` ranked by `matching_fact_count` (decided 2026-10-07), where the LLM runs purely to generate application materials — it has no vote on fit. **Corpus/query direction and granularity (decided 2026-07-22):** `source_of_truth` is the indexed corpus, `job_posting` is the query string, and the corpus is built at one `Document` per atomic fact (every skill, project, known-gap, story, and preference item gets its own `Document`) — so the ranked output is your own facts scored against a given posting, not the posting's requirements scored against your profile. **Pass/fail signal (decided 2026-07-22):** use `rrf_search`'s fused `rrf_score` as-is, keeping both BM25 and semantic search combined via RRF exactly as already built — a raw semantic-similarity score would be more precise but requires code changes to carry it through fusion (currently dropped in `hybrid_search.py`'s final result assembly), and that precision was explicitly declined in favor of using search as it already exists. Known, accepted imprecision: `rrf_score` is rank-based, not similarity-magnitude-based, so a corpus's top-ranked fact scores similarly whether it's a strong match or just the least-bad option. **Threshold rule (decided 2026-07-22, recalibrated 2026-09-30 and twice 2026-10-07):** a posting passes when at least **5** distinct **fit** facts score `rrf_score` ≥ **0.028** against it. Not counted as fit (they stay in the results and reach the generator): gap and screening-answer facts (`known_gap:*`, `job_preference:*`, `professional_experience`) — they matched nearly every posting, e.g. the sales-manager mismatch's top keyword hit was `job_preference:salary_range` via the posting's `salary_range` key — plus `education` (gap material that inflated any posting mentioning a degree) and the logistics preferences `work_mode`, `regions_open_to`, `hard_deal_breakers` (they match any "remote"/"Europe" posting); the `roles` and `tech_stack_priority` preferences still count. Also 2026-10-07: every fact is ranked (no result cap — one that would have started dropping facts once the corpus passed 50), ties are broken by doc id (set iteration order made equal-score facts swap ranks between runs), `profile.summary` is indexed, and the query is the posting's content fields only. Result on the fixtures: relevant 9/8/8 fit facts vs. the mismatch's 2 at 0.028, so a minimum of 5 leaves a 3-fact margin on both sides. History: 0.026 → 0.028 (2026-07-22) → 0.029 (2026-09-30) → 0.028 with min 4 → 0.028 with min 5 (2026-10-07). Still four synthetic fixtures — see `matching/README.md`. Sourcing needs no pre-filter beyond ATS — role/location/tech fit is fully decided at this matching step. Document construction is built: `matching/document_builder/document_builder.py` turns the five `source_of_truth` files into one `Document` per atomic fact (`json.dumps` per fact, no templating) and job postings into query strings the same way (`json.dumps` on the posting JSON). Matching's design is now fully settled end-to-end; only recalibrating the threshold against real data remains. See `matching/README.md`.

**Types (decided 2026-07-22):** `job_posting` and `source_of_truth` entries reduce to the same simple shape for search purposes — `Document(id, content)`, a stable id plus flattened text — so `hybrid_search` can operate on both uniformly (`job_config` no longer participates in search — see Matching approach above). `hybrid_search` returns `id` plus the matched `Document` itself, not bare ids.

**Generator input (revised 2026-08-04, supersedes the id-resolution design this replaces):** the Application Generator consumes the facts that cleared the threshold — `evaluate_posting`'s `matching_facts` (every result with `rrf_score` ≥ the threshold, gap/screening facts included) — as `(id, content)` pairs, exactly as `hybrid_search` returns them. There is no separate top-N cutoff ("top-N" in older notes meant this set). Nothing caps its size; what's enforced is the prompt itself — `llm_ollama()` refuses a prompt that might not fit `NUM_CTX` (a conservative character-count estimate, checked before sending, since Ollama truncates silently) with `PromptTooLongError`. The glue passing it from `matching/` to `generate()` isn't written yet — no separate resolve-by-id step back to a richer structured record. This holds up because `document_builder` builds one `Document` per *atomic* fact, with `content` as plain `json.dumps()` of that single fact — so the flattened string already *is* the structured fact, just serialized, and there's no real structure left to resolve by going back to the source JSON. See `matching/README.md`'s Types section and `tailoring/README.md`'s Generator input note. **Exception — known gaps bypass search (decided 2026-09-30):** the cover-letter call also receives `known-gaps.json` directly, independent of `hybrid_search`'s ranking. Found in a code review: on the Nordbridge fullstack fixture, all four known gaps scored below the 0.028 cutoff, so the generator never saw visa sponsorship/degree/GPA — making the "structurally required" gaps paragraph depend on search ranking. Search still decides fit (deterministic, no LLM); only the generator's *input* changes. **Implemented 2026-09-30:** `generate(..., known_gaps, ...)` runs `decide_gaps()` (plain code, `tailoring/gaps/`) before any LLM call and passes only the gaps the posting asks about — phrasing variant selected, years requirements quoted — to the cover-letter prompt; `CoverLetter.gaps` is required when any gap applies and removed from the schema when none does. Gap-governed facts (`known_gap:*`, `education`, `professional_experience`, `job_preference:*`) are dropped from the resume/cover-letter facts but kept for the application call.

**Tracking:** must be a single store shared across all concurrently-running Go orchestrator instances (reads *and* writes), not local per-instance state — otherwise two instances (e.g. Greenhouse + Lever running at once) could double-apply to the same company/role. In practice this is less about multi-writer coordination than it first sounds: since Python is a shared singleton service (not one per Go instance), every orchestrator's writes funnel through that one process, which serializes them naturally (decided 2026-07-27, see `agent/tracking/` above). **Storage format (decided 2026-07-27): plain JSON files, no database for now** — PostgreSQL is the planned future upgrade once the user sets up a local instance, not the v1 design. `source_of_truth/profile.json` stays read-only and shared by contrast — the pipeline never writes to it.

**Review gate / Application Controller (updated 2026-07-22):** routing to human review is no longer a numeric confidence threshold. A second LLM (the Application Controller, distinct from the Application Generator in `tailoring/` — whether it runs on the same local CPU-only Ollama instance or a separate model/service is not yet decided) checks the generator's output against `source_of_truth` (honesty — is every claim traceable to a real fact) and against the job posting (relevance — does the answer actually address what was asked). Any failure on either check — no distinction in severity between a honesty miss and a relevance miss — routes to human review; passing both sends the application straight to Application API for submission. A user-maintained override list (certain roles/companies always reviewed regardless of the check) still applies on top of this.

No dashboard. Push notification via **email** with clickable approve/reject links fires immediately when something routes to review; a separate end-of-run report (submitted, matched-but-not-submitted, skipped, errors) is generated when an instance times out, for the user to read at their own pace. As of 2026-10-07 it must specifically list: postings skipped as stale (30+ days), company boards that failed to fetch (with the error, e.g. 404), postings that couldn't be normalized, exclusion records written this run (with reason), and reviews that timed out (no exclusion — they'll come back). If the user doesn't respond before the instance's run ends, the item **defaults to reject** — nothing is submitted, but (revised 2026-10-07) no exclusion record is written, so the posting can be reviewed again in a later run; see `agent/tracking/` above.

The review email shows the **full generated package inline** in the body — resume text, cover letter text, filled form field answers — not summarized and not as attachments (attachments are phone friction). Driving reasoning: missing a bad generation in a too-short email is a worse failure mode than a long email, so it errs toward showing everything. It also includes a **log/report-style breakdown of why that specific application was routed to review** (the Application Controller's honesty/relevance verdict and reasoning, or which manual-override rule fired), distinct from the separate end-of-run report that summarizes a whole container run.

**Sending mechanism (decided):** a dedicated Gmail account created specifically for this app sends the review-request emails to the user's personal address, via Gmail's own SMTP/API. Needs no inbound reachability — any container with outbound internet access can send.

**Receiving mechanism (decided):** one extra tap is acceptable — the link opens a confirm page rather than firing the action on a bare GET (bare links risk being auto-triggered by email security scanners/prefetchers before the user ever opens the email). Reachability must work from anywhere, in a normal browser, with no special app installed — this rules out Tailscale (private mesh, requires the Tailscale app on the device) in favor of **Cloudflare Tunnel**: a real public HTTPS URL, free tunnel service, but requires a domain the user controls (~$10-15/year — not yet owned, needs registering) and the link itself becomes a bearer credential needing its own token-based protection since the endpoint is genuinely public.

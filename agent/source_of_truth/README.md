# source_of_truth

Profile store — the structured, hand-maintained source of truth (education, projects, skills, job preferences, etc.) that the agent will draw from to generate per-job resumes/cover letters and score fit. Built from `resume.pdf`, with any gaps filled in by the user directly (never inferred/guessed).

**Expanding from one file to several (decided direction, more may follow).** Currently just `profile.json`. Four planned additions so far:
1. **Projects-detail file** — deeper per-project detail than the `projects` array in `profile.json` (tech stack, turning points, planning process, structure) — giving the LLM honest incident-level material for project-specific behavioral questions ("tell me about a time you solved a bug"), rather than only feature-level bullets.
2. **General-stories file** (built — see `general-stories.json`) — real anecdotes not scoped to any one project, for behavioral questions the projects-detail file can't answer. Three stories so far: rebuilding a broken study streak through visible progress-tracking (deliberately not naming the personal reason for the breaks — kept private per the user, framed only around the observable behavior); choosing to redo the entire Backend Developer Path in TypeScript for depth, not because the language was new; and leaning on AI tools for guided-project research, then actually carrying those concepts into independent projects rather than treating them as one-off exercises.
3. **Known-gaps file**, hand-maintained by the user directly (not pipeline-generated) — honest, pre-considered phrasing for this candidate's recurring gaps (in-progress degree, no professional experience, GPA, sponsorship need). Carries forward the manual cover-letter workflow's stance of naming gaps directly rather than glossing over them (see root `CLAUDE.md`), since a small CPU-only local model is more likely to soften/omit a gap by default, and some pipeline output gets auto-submitted without a human reading it first.
4. **Preferences file** (decided 2026-07-22, built — see `preferences.json`) — a generalized, shared statement of what roles/locations/stacks this candidate is open to: backend developer primary, fullstack/AI-ML also acceptable; remote preferred, open to Europe/USA/Canada; Go and Python prioritized over TypeScript. Replaces what used to be a per-instance `job_config` filter on the Go orchestrator — since it's now one shared set rather than narrowed per run, it belongs here instead. Feeds `matching/`'s single `hybrid_search(job_posting, source_of_truth)` call directly. Distinct from the existing `job_preferences` field in `profile.json`, which answers deterministic screening questions (salary, visa, notice period) — `preferences.json` explicitly points back to `profile.json` for those rather than duplicating them.

EEO/legal-boilerplate answers are also structured fields in `profile.json` (built 2026-07-22, alongside `job_preferences`, as a sibling `eeo` key) — same reasoning as everything else, never left for the LLM to guess. Race/ethnicity is stored as a value plus a note that "decline to state" is always a legally valid alternative, since standard US EEO categories don't map cleanly from nationality. Sexual orientation is stored but flagged "answer only if asked, never volunteer" — it isn't part of the standard EEO/veteran/disability disclosure set most forms actually request.

**Deterministic vs. generative split:** work authorization, visa sponsorship, salary, notice period, language, and EEO questions are answered directly from structured fields here — no LLM involved. The LLM only touches this store for generative work (resume tailoring, cover letters, free-text behavioral questions), always adapting real content from these files, never inventing. No answer caching for now — regenerated fresh every time.

Stays a single shared, read-only resource across every running Go orchestrator instance (see deployment model in `../README.md`) — no per-instance customization of the profile store itself. Read directly by the Python service's `sourcing/`, `matching/`, and `tailoring/` modules (see tech stack in `../README.md`); Go and TypeScript work from Python's generated output rather than reading `profile.json` themselves.

Done, in use — see `profile.json`. Everything else in `../` is still planning stage; see `../CLAUDE.md`.

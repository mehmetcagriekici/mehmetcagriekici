# review_gate

**Pipeline role: Application Controller.** Third stage of `Data -> Hybrid Search -> Application Generator -> Application Controller -> Application API`. A second LLM — distinct from `tailoring/`'s Generator — checks the Generator's output against `source_of_truth` (honesty: is every claim traceable to a real fact) and against the job posting (relevance: does the answer actually address what was asked). It isn't re-judging fit — `matching/` already decided that deterministically; this is QC on what the Generator produced.

Any failure on either check — no severity distinction between honesty and relevance — routes to human review. Passing both sends the application straight to `form_automation/` for submission. A user-maintained override list (always review certain roles/companies regardless of the check) applies independently on top of this.

**Language: Python** — internal module of the shared Python service, not routed through Go.

**Notification:** no dashboard. A push email fires immediately when something routes to review, with clickable approve/reject links. If the user doesn't respond before that instance's run times out, the item defaults to reject — nothing submits without explicit approval — but no exclusion is recorded, so the posting can come back in a later run with a fresh email. The same holds for a one-page overflow still unanswered at run end. A link tapped after its run has ended opens a page saying it expired and the posting will come back, rather than acting. The user's explicit reject writes a permanent exclusion record to `tracking/`, so that posting never comes back. The Controller itself never rejects or excludes — every failed check only routes to the user's review (decided 2026-10-08). Separately, each instance also produces an end-of-run report summarizing everything it did, for the user to read at their own pace.

**Email content:** the full generated package shown inline (resume text, cover letter text, filled form field answers) — not summarized, not attachments, since missing a bad generation in a too-short email is worse than a long one. Also includes a log/report-style breakdown of why that application was routed to review (the honesty/relevance verdict and reasoning, or which override rule fired).

**Mechanism:** a dedicated Gmail account sends the emails via Gmail's own SMTP/API — no inbound reachability needed. The approve/reject tap opens a one-tap confirm page rather than firing on a bare link (bare GET links risk being auto-triggered by email security scanners before the user opens the email). That page is reached via a Cloudflare Tunnel — chosen over Tailscale so it opens straight from Gmail in a normal browser with no app install. Requires a domain the user controls (not yet owned) and a token-protected link, since the endpoint is public.

## Honesty check: code first, then the LLM (decided 2026-10-08)

The honesty check starts with a **deterministic check in code**: any technology named in the model-written text that doesn't appear in the facts that model was given is flagged. It runs in milliseconds with no LLM, and targets the failure every live run has shown (the 2026-10-07 letter credited BlightSanest with React and the Pub/sub CLI with Node.js/Express). An LLM check then covers only what code can't decide — relevance, and claims that aren't about technology ("databases at scale", "production"). What it checks is refined (2026-10-08): **any name-like word**, not only technology — code can't tell from plain text that "React" is a technology and "Berlin" isn't without a hand-kept dictionary, and the invented words (React, Node.js, Express) came from the posting, not the facts, so a vocabulary built from the facts alone would miss them. A word is name-like by its shape: capitalized mid-sentence, mixed case (gRPC, TypeScript), containing a dot (Node.js), or all caps (AWS, CI/CD); a small stop list skips ordinary sentence-initial words. It's flagged when it doesn't appear in the facts the model was given.
- **Checked:** text that describes the candidate — the resume (summary, project tech, descriptions, bullets, skills) and the cover letter's `experience` and `stack_gap`. **Not checked:** the letter's `why`, which legitimately names the job's own technologies ("your Node/Express API"); it's left to the LLM check.
- **On a flag:** routed to the user's review email, with the flagged words listed as the reason — not a permanent exclusion, since the check is crude and the user should have the final say.

**The LLM check runs on the 14B, on every application (decided 2026-10-08)** — the same `qwen2.5:14b` as the generator, as a separate call (the earlier open question "same model or separate?" is settled: same model). It covers what the name check can't: upgraded claims without names ("databases at scale", "experienced"), and relevance, including the letter's `why`. Cost accepted: ~15 more minutes per application (~75 in total), so a 24-hour run yields roughly 19 applications. Considered and not chosen: a smaller model for the check (unknown reliability), and no LLM check in v1 with every application going to the user's review.

**How the LLM check works (decided 2026-10-08)** — set up so the model can't simply approve output like its own:
- **Sentence by sentence, with evidence code verifies.** Code splits the model-written text into sentences; for each, the check answers supported or not, and if supported, quotes the exact words from a fact that support it. Code then checks the quote really appears in the given facts — an invented or loose quote counts as unsupported. Any unsupported sentence routes to review.
- **Which sentences need evidence — decided by section, in code, not by the model:** every sentence in text that describes the candidate (the resume, the letter's `experience` and `stack_gap`, and free-text form answers) needs a verified quote. The letter's `why`, the one place motivation belongs ("I'd like to work on payment infrastructure"), gets only the relevance check. Rejected: letting the model label each sentence as claim or motivation — a fabrication labelled "motivation" would slip through. Consequence accepted: `experience` must stay strictly factual ("this taught me a lot about distributed systems" is flagged unless a fact says so).
- **Relevance:** one yes/no per application with a one-line reason (does the `why` actually connect to the posting?) — it can't be checked by quote; a "no" routes to review.
- **Order:** the name check runs first; if it already flagged something, the LLM check is skipped (the application goes to review anyway, so the ~15 minutes would be wasted). Considered and not chosen: a second LLM judging the whole output (the same kind of model judging prose, ~15 min more per application), and having the model list each claim with its supporting fact (it wouldn't list its own fabrications).

## Override list (decided 2026-10-08)

A hand-maintained JSON file in this folder forces review regardless of the checks — an application that matches any entry goes to the user's review email even if every check passed. Each entry matches on **`company`** (exact display name — e.g. companies the user would rather check by hand) and/or a **word in the title** (e.g. "Senior", "Lead" — roles to apply to only deliberately), with a **`note`** that's shown in the review email as the reason. Like the company list, the pipeline never writes to it.

## What live runs say the Controller must catch

Four live runs of `tailoring/` against local Ollama (2026-08-05 and 2026-09-30, 7B model) produced output that passed every structural check — valid JSON, schema-valid, one page — but was not honest. Fixed upstream since: invented company names (a context-window truncation), placeholder form-answer keys, visa/GPA gaps raised unasked (now decided in code). Still seen on the last 7B run, and exactly the Controller's job:
- **Upgraded claims:** "Go in production systems", "databases at scale", "Experienced backend engineer… proven track record" — against facts saying the Go API is in early bootstrap and gRPC "not yet started".
- **Dropped hedges:** "Kubernetes/EKS" listed plainly where every fact says experimental.
- **Misattribution:** a technology credited to a project whose fact doesn't list it.
- **Filler** despite being banned by name ("strong background", "I believe my skills align well").

The 14B live run (2026-10-07) fixed the misattribution and the "production"/"at scale" claims and described an early-stage project honestly, but still produced filler ("I am excited to apply", "passion"), an upgraded claim ("Experienced backend engineer"), an unsupported "frontend" claim echoing the posting's wording, and a phrasing-rule instruction from `known-gaps.json` copied into a letter. Since then the cover letter's fixed parts (opening sentence, gaps paragraph, closing) are written by code, which removes the filler slots and the instruction-copying route structurally; upgraded and unsupported claims in the model-written parts remain the Controller's job. The Controller's two checks (above) are designed to catch exactly these.
